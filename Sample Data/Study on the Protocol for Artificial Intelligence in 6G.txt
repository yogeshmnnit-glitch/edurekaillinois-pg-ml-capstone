Introduction
This Technical Report aims at studying the requirements on the Stage 3 protocols to enable the support and use of AI in 6G.
 
1	Scope
The present document studies Stage 3 protocol aspects for supporting and enabling the use of AI (e.g. AI Agent, intent) in 6G, taking into account the architectural requirements defined by SA2 in 3GPP TR 23.801-01 [4], and the security requirements defined by SA3 in 3GPP TR 33.801-01 [5].
The study covers candidate protocols and protocol design considerations to support AI (e.g. AI Agent, intent) in 6G. It addresses Stage 3 protocol aspects for enabling AI-related services, such as exposure, discovery, authorization, and invocation of AI capabilities. The study also considers protocol support for possible interworking with other protocols in 6G, as well as interworking aspects between 5GS and 6GS with regards to AI protocols.

4	Protocol requirements and assumptions
This clause describes protocol requirements and assumptions, if required.
4.1	Protocol requirements
The protocol studied for supporting and enabling the use of AI (e.g. AI agent, intent) in the 6G shall support the following requirements.
4.1.1	AI-Agent related protocol requirements
The protocol should support the following AI-Agent aspects, as applicable to Agent-to-Agent and Agent-to-Tool interactions:
-	interactions involving AI agents (Agent-to-Agent), and interactions between AI agents and tools, resources, services; and
-	extensibility to accommodate new AI-Agent related requirements subjects to operator’s policies.
4.1.2	Intent related protocol requirements
The protocol should support the following intent related capabilities:
-	exchange of intent-related information between entities;
-	exchange of information that enables the translation of intent-related information into actions, requests, tasks and/or operations;
-	exchange of result, failure and error information associated with intent fulfilment; and
-	extensibility to accommodate new intent-related requirements subjects to operator’s policies.

-	It allows to identify the entities to handle and fulfil the intent.
-	It allows to correlate intent and the corresponding intent fulfilment status.

5.2	Candidate protocols
5.2.1	General
This clause documents the candidate AI-related (e.g. AI Agent, intent) protocols for the 6GS.
5.2.2	Model Context Protocol (MCP)
5.2.2.1	General
The model context protocol (MCP) is a stateless client-server protocol built on the JSON-RPC 2.0, defining a standardized framework for enabling AI agents to communicate with external tools and data sources.
The MCP is an open-source semantic interaction protocol utilized in the generative AI industry. MCP was first proposed by Anthropic on November 25, 2024, and now it have been donated to the Linux Foundation’s new Agentic AI Foundation by Anthropic. Implementations of MCP are available at MCP Open Source Project [2].
The MCP enables AI models to securely discover and invoke external capabilities via abstract resource identifiers. The MCP can be a candidate protocol for its ability to provide semantic translation and map abstract AI intents to logical network capabilities, required context, and deterministic execution commands. The MCP may be able to bridge the sufficient gap for autonomous AI entities that must dynamically consume network capabilities, e.g. by defining three server-side primitives (Tools, Resources, and Prompts) and client-side features such as Elicitation.
5.2.2.2	Architecture
Three participants are defined in MCP, as shown in figure 5.2.2.2-1:
-	MCP Host: The AI application (e.g., an AI agent or a LLM application) that coordinates and manages one or multiple MCP clients;
-	MCP Client: A component that is created by the MCP host and communicates with exactly one MCP server and obtains context from the server for the MCP host to use;
-	MCP Server: A program that provides specialized context and capabilities to MCP clients;
 
Figure 5.2.2.2-1: Three participants defined in MCP
5.2.2.3	Protocol stack
The protocol stack of MCP includes two core layers:
-	Data layer, which defines the JSON-RPC based protocol for client-server communication, including protocol versioning and compatibility, message patterns, and core primitives, such as tools, resources, prompts and notifications;
-	Transport layer, which defines the communication mechanisms and channels that enable data exchange between clients and servers, including transport-specific connection establishment, message framing, and authorization.
For remote server communication, MCP adopts streamable HTTP transport. Specifically, streamable HTTP transport uses HTTP POST for client-to-server messages with optional Server-Sent Events [17] for streaming capabilities. Standard HTTP authentication methods including bearer tokens, API keys, and custom headers are also supported. OAuth [19] is recommended by MCP to obtain authentication tokens.
MCP also defines a stdio transport for direct process communication between local processes on the same machine. Stdio transport refers to the Standard Input/Output (Standard I/O) transport method, enables MCP client and server communicate directly by sending JSON-RPC messages back and forth through the standard I/O streams.
MCP is a transport-agnostic protocol and allows clients and servers implementing custom transports to suit their specific needs. However, it requires that any implementations must preserve the JSON-RPC message format and message direction, request metadata and cancellation requirements defined by MCP.
5.2.2.4	Transport layer
The protocol currently defines two standard transport mechanisms for client-server communication. For details about the streamable HTTP transport and stdio transport, please refer to MCP base protocol [3].
5.2.2.5	Data layer
The data layer implements a JSON-RPC 2.0 based exchange protocol that defines the message structure and semantics. This layer includes per-request protocol metadata and server discovery, core primitives and notifications.
Primitives define the functionalities/features that clients and servers can offer each other. Different primitives specify the types of contextual information that can be shared with hosts and the range of actions that can be performed.
At the server side, MCP defines three core primitives that can be exposed:
-	Tools: Executable functions that the host can invoke to perform actions.
-	Resources: Data sources that provide contextual information to the host.
-	Prompts: Reusable templates that help structure interactions with language models.
Detailed information about these client and server features/primitives can be found at: MCP base protocol [27]
Notification enables MCP servers to provide real-time updates to connected clients. Notifications are sent as JSON-RPC 2.0 notification messages (without expecting a response).
Additional information about the utility features can be found at MCP base protocol [27].
5.2.2.6	MCP protocol procedures
5.2.2.6.1	General
MCP uses a stateless protocol core based on self-contained requests. This clause summarizes only the MCP protocol behaviour relevant to the present protocol analysis. Detailed operation names, message fields and transport-specific procedures are specified by MCP [27].
5.2.2.6.2	Capability and protocol-version handling
The MCP client and MCP server need to use protocol version and applicable capabilities. MCP provides means for a client to obtain or verify the versions and capabilities supported by a server.
5.2.2.6.4	Asynchronous updates
MCP provides mechanisms for a client to receive asynchronous updates when information changes or when an interaction continues over time. The applicable update mechanism depends on the supported protocol capabilities and transport.
5.2.2.6.5	Progress and cancellation
MCP provides mechanisms for indicating progress and for requesting cancellation of in-progress work where supported. The detailed cancellation behaviour depends on the applicable protocol and transport behaviour.
5.2.2.7	Security
5.2.2.7.1	General
MCP [27] incorporates security mechanisms to protect access to tools, resources, prompts, and other capabilities exposed by MCP servers. For remote communications, MCP reuses established Internet security and identity management frameworks rather than defining protocol-specific security procedures.
5.2.2.7.2	Authorization
MCP Authorization is optional for MCP implementations. The MCP authorization framework is based on existing standards including OAuth 2.1 as defined in draft-ietf-oauth-v2-1 [19], OAuth Bearer Token Usage as defined in IETF RFC 6750 [20], OAuth Authorization Server Metadata as defined in IETF RFC 8414 [21], Resource Indicators for OAuth 2.0 as defined in IETF RFC 8707 [22], OAuth Authorization Server Issuer Identification as defined in IETF RFC 9207 [23], OAuth Protected Resource Metadata as defined in IETF RFC 9728 [24], OAuth Client ID Metadata Documents as defined in draft-ietf-oauth-client-id-metadata-document [25], and OpenID Connect Discovery [26].
Editor's note:	The feasibility of 3GPP based authentication/authorization of agentic communication using MCP will be determined by SA3 and CT3 will take these determinations into consideration.
5.2.2.8	Versioning Handling
MCP uses date-based protocol version identifiers in the YYYY-MM-DD format. A new protocol version identifier is assigned when backward-incompatible changes are introduced.
5.2.3	Agent Network Protocol (ANP)
5.2.3.1	General
The Agent Network Protocol (ANP) is an open source agent communication protocol designed to enable interoperable communication and collaboration among AI agents. ANP aims to define how agents connect with each other in an open, secure and efficient collaboration network [6]. A key design principle of ANP is the absence of a central authority, i.e. a decentralized architecture. ANP can be deployed on existing Internet infrastructure such as DNS, HTTPS, web servers and DID mechanisms [7]. Its modular design allows an implementation to adopt selected components, for example identity and description, or to combine identity, discovery and messaging into a more complete agent-to-agent communication stack. This makes ANP relevant as a candidate for 3GPP analysis because AI Agent protocol studies in 6G can include a range of deployment models, from exposure of a single network-side agent to interaction among agents in different administrative domains. ANP can be considered as a candidate AI Agent related protocol for analysis in WT#1.
The ANP specifications are organized as a layered protocol suite. The identity and namespace layer includes did:wba and WNS, which provide verifiable agent identities, human-readable handles and cross-domain trust roots [8]. The description and discovery layer enables agents to publish capabilities and find interoperable services [9], [11]. The communication meta-protocol provides negotiation patterns for agents to exchange protocol capabilities and choose interoperable interaction paths [12]. The messaging profiles cover direct messaging, group messaging, E2EE, attachment/object transfer and federation semantics [10]. Application protocols can be built on top of the common identity, authorization and evidence mechanisms.
 
Figure 5.2.3.1-1 Three-layer protocol architecture in ANP
Editor’s Note: The referenced specifications for the instant messaging protocol [10], agent discovery protocol [11] and Meta-protocol [12] are currently in draft status. The associated text may need to be updated once these specifications are stabilized.
The following clauses describe key aspects of ANP that can be considered in WT#1.
5.2.3.2	Agent identity and trust establishment
ANP treats agent identity as a fundamental primitive. The did:wba method is a web-based DID method designed for cross-platform identity authentication and agent communication [8]. A DID document can include verification material and service endpoints associated with an agent, including the AgentDescription service and ANPMessageService endpoints. In this model, an agent can have a stable agent DID that is independent of an implementation instance, terminal or worker node.
5.2.3.3	Agent description and discovery
ANP defines an Agent Description Protocol that uses JSON as the basic data format and supports linked-data and semantic-web features [9]. ANP also defines an Agent Discovery Protocol that uses JSON-LD and includes active discovery through well-known URI paths and passive discovery through search services [11]. An agent description can contain basic agent information, product or service information, capabilities, interfaces, protocol endpoints, supported interaction protocols and security schemes. The Agent Description specification also supports interoperability with existing standard protocols, for example OpenAPI and JSON-RPC, enabling an agent to expose both human-readable and machine-readable information.
5.2.3.4	Protocol negotiation and interoperability
ANP includes a communication meta-protocol concept, where agents can exchange protocol capabilities and select an interoperable interaction path based on LLM [12]. Combined with agent descriptions, this can allow an initiating agent to determine whether the peer supports a given interface, security mechanism, message format or application protocol. This approach is useful when multiple candidate AI Agent protocols or application-level protocols coexist.
5.2.3.5	Cross-domain agent messaging and collaboration
ANP end-to-end instant messaging is a family of specifications for cross-domain messaging between agents. It covers discovery of peer agents, direct messages, group messages, E2EE, attachment and large object transfer, and routing, relaying, sorting and result witnessing in cross-domain scenarios [10]. ANP identifies the protocol endpoint as the agent, rather than the device, terminal or internal replica. It also describes a federated architecture in which identity and service endpoints are distributed across domains.
The messaging profiles distinguish control-plane functions, such as group creation, member management, capability negotiation, ticket issuance and cross-domain service invocation, from data-plane functions, such as direct messages, group messages and attachment object content. This separation can be useful for analysing how AI Agent messages are established, routed, authorized and protected.
5.2.3.6	Multi-modality
The ANP protocol supports the transmission of multi-modal data between agents, the multi-modal data including nature language and structured interface, which are defined in "interfaces" parameter in the Agent Description.
5.2.4	Agent2Agent (A2A)
5.2.4.1	General
A2A is an open-source protocol framework defining canonical data models (e.g., Task) and interaction schemas for multi-agent collaboration. A2A can be a candidate protocol to evaluate payload formatting for asynchronous task negotiation and multi-turn message exchanges to support multi-agent collaboration.
-	A2A supports Task State Machine (Submitted->Working->Input_Required-> Completed/Failed). This allows manage and track the lifecycle of long-running, multi-turn AI interactions without maintaining redundant, stateful network. 
-	A2A's modality-agnostic "Part" structure supports the negotiation and transmission of multi-modal payloads, which is essential for low-latency, real-time autonomous collaboration.
-	A2A supports multiple protocol bindings (e.g., HTTP/REST, JSON-RPC [16], and gRPC [18]) to ensure flexible and interoperable agent communication. Mapping the protocol's abstract data models to these diverse transport mechanisms enables seamless integration across different platforms and frameworks, enhancing network scalability and deployment adaptability.
5.2.4.2	A2A Protocol Design principles
The key design principles followed by A2A described in [13] are:
-	Simple: Reuse the existing standards e.g., the HTTP defined in IETF RFC 9110 [15], JSON-RPC 2.0 [16] by the JSON-RPC 2.0 specification, Server-Sent Events [17] as specified by WHATWG HTML Standard.
-	Asynchronous First: Designed for long-running task and human-in-the-loop interactions.
-	Modality Agnostic: Support exchange of diverse content types including text, audio/video.
-	Opaque execution: The collaboration between agents are based on declared capabilities and standard message, without sharing internal implementations.
The three distinct layers of A2A protocol described in [13] includes:
-	Layer 1: Canonical Data Model defines the core data structures including e.g., Task, Artifact, Part and message using Protocol Buffers.
-	Layer 2: Abstract Operations defines the key operations including e.g., SendMessage, SendStreamingMessage etc.
-	Layer 3: Protocol Bindings provides three equivalent mappings of the abstract operations and data structures to specific protocol bindings, i.e., JSON-RPC [16], gRPC [18] and HTTP/REST.
5.2.4.3	Key elements of A2A Protocol
5.2.4.3.1	Agent Discovery
Three discovery mechanisms defined by A2A are supported:
-	Well-Known URI: An agent which is designed for broad discovery within a specific domain can publish its Agent Card (structured, machine-readable manifest) at /.well-known/agent-card.json following the principles defined in IETF RFC 8615 [14].
-	Curated Registry: A centralized repository where agents register their information and the clients query by skills or other information.
-	Direct Configuration: The clients are directly pre-configured with the related Agent Card information or URLs utilizing hardcoded details, configuration files, environment variables or proprietary APIs.
5.2.4.3.2	Interaction Modes
There are three complementary mechanisms for clients to receive the updates of the task progress in A2A protocol:
-	Polling: The client sends GetTask periodically to check the task status. This mechanism is easily to be implemented, but may cause unnecessary signalling.
-	Streaming: The events will be returned in a real-time way to the client. This mechanism is suitable for low latency communication scenario, but requires persistent connection between the client and the server.
-	Push Notifications: A push-notification configuration may be provided when initiating an interaction or it may be created for an existing Task. The agent sends the HTTP POST requests to client-registered endpoints when the state of the task changes, and the client does not need to maintain persistent connection. The notification payload uses the A2A format and convey the corresponding task, message, status-update or artifact-update information. Push notification allows Task updates to be delivered without maintaining a persistent A2A streaming connection and the A2A server attempts notification delivery according to the A2A push-notification procedure as defined in A2A Protocol [13].
Editor's note:	Depends on Stage 2 FFS on the identified security threats of Push Notification and whether the network should accept the callback or not, when considering A2A use in 3GPP.
5.2.4.3.3	Multi-modal Data Transimission
The A2A protocol supports the negotiation and transmission of multi-modal data:
-	When the client sends a message to the agent, "Part" is the container of the message content and used to carry e.g., pure text, image, video, structured data, raw file and URL. The "accepted_output_modes" parameter is carried to indicate the output data formats can be accepted by the client.
-	When the agent sends a response message to the client, the "Part" structure in the artifact is used to carry the output data in one or more modes which are supported by the client.
5.2.4.3.4	A2A Protocol Extensions
The A2A Protocol extensions mechanism provides additional functionality, data, requirements, RPC methods or state machines beyond the core specification while maintaining backward compatibility and interoperability.
Clients and agents negotiate to determine which extensions are active for a specific request.
1.	Client Request: A client requests the list of extension activation to the agent.
2.	Agent Processing: Agents perform the activation.
3.	Response: the response should include all extensions that were successfully activated for that request.
An extension can be used for one or more of the following purposes: Data-only extension, Profile extension, Method extension and State-machine extension. An AgentExtension may include uri, description, required and params. Extensions are inactive by default.
5.2.4.3.5	Fundamental communication elements
5.2.4.3.5.1	Agent Card
The Agent Card is a JSON document that serves as one of the discovery mechanisms (see clause 5.2.4.3.1). It provides essential metadata about an agent. Clients parse this information to determine if an agent is suitable for a given task, how to structure requests, and how to communicate securely. 
The detailed Agent Card object, please refer to clause 4.4.1 of A2A [13].
5.2.4.3.5.2	Task
Task object is the core unit of action for A2A. It has a current status and when results are created for the task they are stored in the artifact. If there are multiple turns for a task, these are stored in history.
The detailed Task object, please refer to clause 4.1.1 of A2A [13].
The Task state machine supports asynchronous, long-running interactions with human-in-the-loop interruptions, enabling clients to track task progress via the polling, streaming or push notification interaction modes described in clause 5.2.4.3.2.
5.2.4.3.5.3	Message
Message object represents a single turn of communication between a client and an agent. It includes a role ("user" or "agent") and a unique message Id. It contains one or more Part objects, which are granular containers for the actual content. This design allows A2A to be modality independent.
Message can be associated with a context and/or a task. For server messages, context Id must be provided, and task Id only if a task was created. For client messages, both fields are optional, with the caveat that if both are provided, they have to match (the context Id has to be the one that is set on the task). If only task Id is provided, the server will infer context Id from it.
For the detailed Message object, please refer to clause 4.1.4 of A2A [13].
The Role enumeration identifies the sender of a Message in A2A communication defined in clause 4.1.5 of A2A [13].
5.2.4.3.5.4	Part
The Part object is a modality-agnostic container that can hold different types of content using a one of field structure. For the detailed Part object, please refer to clause 4.1.6 of A2A [13].
5.2.4.3.5.5	Artifact
The Artifact object representing task outputs is defined in clause 4.1.7 of A2A [13].
5.2.4.4	A2A Implementations and Protocol Bindings
The A2A protocol adopts a layered architecture consisting of a canonical data model, abstract protocol operations, and protocol bindings. The Protocol Bindings of A2A provides concrete mappings of the abstract operations and data structures to specific protocol bindings (JSON-RPC [16], gRPC [18], HTTP/REST), including method names, endpoint patterns, and protocol-specific behaviors.
A2A currently defines the following protocol bindings:
-	JSON-RPC [16] binding, which maps A2A operations to JSON-RPC procedures and supports deployment across environments supporting JSON-RPC exchanges;
-	gRPC binding [18], which maps A2A operations to gRPC remote procedure calls and supports efficient service-to-service communication and streaming interactions;
-	HTTP/REST binding, which maps A2A operations to HTTP-based resource-oriented interfaces using JSON representations and web-based communication mechanisms.
The common canonical data model ensures that equivalent A2A semantics can be supported across different protocol bindings.
